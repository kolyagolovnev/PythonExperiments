# 1. VkazarmePython — основной проект (WIP)

## Что это

Учебный backend социальной сети для бывших сослуживцев. Идея: дать людям, служившим в одном подразделении, возможность находить друг друга, объединяться в группы, публиковать записи, комментировать и общаться в чатах.

Функциональные требования из OpenAPI-спецификации:

- создание и редактирование профиля;
- записи в профиле и группах;
- поиск, добавление и удаление друзей;
- личные и публичные чаты;
- поиск, подписка и отписка от групп;
- комментарии к записям.

**Статус:** WIP. Это не готовый продукт, а полигон для изучения SQLAlchemy, FastAPI и Pydantic. Спецификация API описана полностью, архитектура слоёв заложена, часть эндпоинтов пока являются заглушками.

## Что уже сделано

### 1. Контракт API

- `api_specification/openapi.yaml` — OpenAPI-спецификация (идеальный RestAPI не получился, слишком много спорных моментов было).
- `api_specification/asyncapi.yaml` — описание realtime-канала (пока что оставленное на 2-й план).

Это даёт навык **contract-first / spec-first разработки**: сначала описывается контракт, потом реализация.

### 2. Слоистая архитектура

```
HTTP (FastAPI routers / main.py)
  └─ services/        бизнес-правила, проверки прав, сценарии
       └─ repositories/   интерфейсы (ABC) + реализации
            └─ SQLAlchemy 2.0 + PostgreSQL
  domains/models.py   доменные dataclass-сущности
  dto.py              Pydantic-модели запросов/ответов
```

- **Domain** — обычные `dataclass`, не зависящие от FastAPI и SQLAlchemy.
- **DTO** — Pydantic-модели с валидацией на границе приложения.
- **Services** — бизнес-логика, не знающая про HTTP.
- **Repositories** — абстракции хранения; сервисы зависят от интерфейсов, а не от конкретной БД.
- **main.py** — тонкий HTTP-слой, который собирает зависимости и транслирует исключения в HTTP-коды.

### 3. Нестандартные решения, которые я освоил

**Generic-фабрика зависимостей FastAPI.** Вместо ручного дублирования `Depends` для каждого сервиса написана функция `create_service_dependency(service_cls, repo_cls)`, которая создаёт пару "репозиторий" -> "сервис" и автоматически подставляет её в роутеры. Также я таким образом пытался закрепить каждому типу сервиса свой класс репозиториев, объединенных общим базовым абстрактным классом (как в языках программирования C++). 

**Автоматическая конвертация DTO ↔ Entity.** В `app/dto.py` реализован обобщённый `DTOBase[T_Entity]`:

- `to_entity()` рекурсивно превращает DTO в доменную сущность, включая вложенные объекты и списки;
- `from_entity()` собирает DTO из сущности, игнорируя лишние поля;
- поддерживаются переименования полей через `FIELD_MAPPING` и `FIELD_RENAME_MAP`;
- используются `TypeVar`, `Generic`, `get_args`, `model_fields` Pydantic v2.

Это упражнение в **typing, generics, рефлексии Pydantic и снижении boilerplate**, в котором я пытался закрепить .

**Конфигурация через Pydantic Settings.** `app/settings.py` читает `.env`, хранит секреты, настройки JWT, bcrypt и параметры OAuth. Это приучает не хардкодить конфигурацию в коде.

**Асинхронный SQLAlchemy.** В `main.py` создаётся `create_async_engine` и `async_sessionmaker`; сессия выдаётся через `get_db()` как FastAPI-зависимость. В `sqlalchemy_sign_repository.py` описана Declarative-модель `Account` с `UniqueConstraint` по паре «провайдер + внешний ID».

### 4. Аутентификация и регистрация

- `SignService` валидирует email регулярным выражением, проверяет занятость адреса и хеширует пароль через **bcrypt**.
- JWT проверяется через `PyJWT`; payload валидируется Pydantic-моделью `AuthTokenDTO`.
- Используется `OAuth2PasswordBearer`, обрабатываются `ExpiredSignatureError` и `InvalidTokenError`.
- В `repositories/base.py` описаны интерфейсы `SignRepository`, `AuthRepository`, `UserRepository`, `GroupRepository`, `PasteRepository`.

### 5. Тесты

`tests/unit/test_sign_service.py` — unit-тесты сервиса регистрации:

- 8 тестовых функций, часть параметризована наборами валидных и невалидных email;
- проверка формата email, занятости адреса, порядка вызовов репозитория;
- проверка, что пароль не хранится в открытом виде и корректно проверяется через `bcrypt.checkpw`;
- репозитории заменены `AsyncMock`/`MagicMock` — сервис тестируется изолированно от БД.

### 6. Инфраструктура

- Многоступенчатый `Dockerfile`: `base` → `prod` → `test-base` → `lint` → `test-unit` → `test-e2e`.
- `docker-compose-tests.yml` поднимает PostgreSQL для тестов.
- `docker-compose.yml` поднимает Swagger Editor для работы со спецификацией.
- `requirements-dev.txt`: `pytest`, `pytest-asyncio`, `pytest-cov`, `pytest-xdist`, `httpx`, `testcontainers`, `mypy`.

## Чему я научился

- Проектировать API до кода и держать реализацию в соответствии со спецификацией.
- Разделять домен, DTO, сервисы и репозитории, чтобы бизнес-логика не зависела от FastAPI и БД.
- Работать с Pydantic v2: `BaseModel`, `Field`, `EmailStr`, `AnyUrl`, `RootModel`, `ConfigDict`, generic-модели.
- Строить DI в FastAPI, в том числе генерировать зависимости через фабрики и `TypeVar`.
- Использовать async SQLAlchemy 2.0: engine, sessionmaker, `Mapped`, `mapped_column`, DeclarativeBase.
- Писать unit-тесты с `pytest`, `pytest-asyncio` и `AsyncMock`, не поднимая реальную БД.
- Хешировать пароли через bcrypt и проверять JWT, не путая аутентификацию с авторизацией.
- Собирать multi-stage Docker-образы и запускать тесты в контейнерах.

## Что пока не готово / известные ограничения

Проект пока не завершен (мне очень не хочется тратить на него время, чтобы забесплатно доводить его до конца руками). Основные пробелы:

- многие эндпоинты в `main.py` — заглушки (`pass`) или возвращают пустые списки;
- CRUD-операции SQLAlchemy-репозиториев ещё не реализованы;
- нет Alembic-миграций и полноценного unit-of-work: каждая операция репозитория — отдельная транзакция;
- обработка ошибок в HTTP-слое местами слишком широкая (`except:` → 400);
- нет полноценного e2e-набора для текущей версии;
- чтение и запись разделены не до конца: часть проверок прав пока живёт в сервисах-заглушках;
- OAuth2 и подтверждение email сознательно исключены из этой версии.

```bash

python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
pytest tests/unit -v
```

# 2. VkazarmePython_failed — расширенная версия (архив)

## Что это

Более амбициозная версия того же проекта. В ней я попытался сразу реализовать то, что обычно требуется от «настоящего» backend:

- регистрацию и вход через **OAuth2** (Google и VK);
- **подтверждение email** с отправкой письма и одноразовым ключом;
- хранение временных аккаунтов в **Redis** с TTL;
- мок-серверы внешних OAuth-провайдеров для тестов;
- более полную схему PostgreSQL.

**Статус:** остановлена. Я сознательно отказался от OAuth2 и email-подтверждения в текущей версии: для учебного проекта это добавило слишком много инфраструктуры (внешние сервисы, SMTP, DNS, мок-провайдеры, nginx, обработка ошибок), не дав соразмерного прироста в понимании основных слоёв приложения. Проект сохранён как архив и как источник выводов.

## Что было сделано

### OAuth2

- Эндпоинт `/account/signin/init` генерирует `state` через `secrets.token_bytes` — защита от CSRF.
- Эндпоинт `/account/signin/oauth2/{provider}/callback` принимает `code` и `state`.
- `Provider` enum: `VK`, `GOOGLE`, `SELF`.
- `tests/mock_servers/mock_provider_server.py` — FastAPI-мок, эмулирующий `/authorize` и `/token` для Google и VK:
  - редирект с одноразовым `code`;
  - проверка `client_id`;
  - выдача `access_token`, `refresh_token` (только для Google), `id_token`;
  - эмуляция ошибок и задержек.
- `tests/mock_clients/mock_client.py` — клиент, который проходит полный OAuth-flow: получает `code` из редиректа, обменивает его на токены, проверяет ошибки и таймауты.
- `oauth2_vk_nging.conf` — заготовка nginx-конфига для подмены хостов `oauth.vk.com` и `oauth2.googleapis.com` на мок-серверы.
- `docker-compose_test.yml` — сеть с фейковым OAuth-провайдером и тестовым клиентом.

### Подтверждение email

- `MailSubService.validateEmailAndGetSmtp()`:
  - проверяет структуру адреса;
  - запрашивает **MX-записи** домена через `dnspython`;
  - сортирует MX по приоритету;
  - отсеивает временные почты по ключевым словам в имени MX-сервера;
  - выбирает SMTP-сервер для Gmail, Yandex, Mail.ru, Outlook или корпоративного домена.
- `MailSubService.sendEmail()` отправляет HTML-письмо через `smtplib` с `starttls` и логином.
- `SignService.signUp()` создаёт временный аккаунт в Redis с TTL и отправляет ссылку подтверждения.
- `SignService.signUpConfirm()` сверяет ключ и переносит аккаунт в постоянное хранилище.
- `RedisCacheSignRepository` хранит временные аккаунты по ключу `accounts:{email}` с истечением срока.
- `tests/e2e/test_mail_signup.py` — сценарий: регистрация → вход до подтверждения (403) → получение письма из Mailpit → подтверждение → успешный вход → вход с несуществующим аккаунтом (404).

### База данных

`db/init_db.sql` — схема из 10 таблиц:

- `accounts`, `users`, `groups`, `friends`, `subscriptions`;
- `pastes` (посты), `comments`;
- `chats`, `chat_members`, `messages`.

В схеме есть внешние ключи с `ON DELETE CASCADE`, `UNIQUE`-ограничения, `CHECK` на невозможность добавить себя в друзья, перечисление `PROVIDER_ENUM`. Также созданы три роли PostgreSQL: `simple_user`, `admin`, `readonly` — попытка следовать принципу наименьших привилегий.

### Тесты и процесс

- 14 e2e-тестов в стиле BDD (Given/When/Then) для аккаунта, пользователей, друзей, групп, постов, комментариев, чатов и медиа.
- Часть тестов — черновые заготовки: некоторые сценарии требуют предварительно созданных сущностей и не были доведены до зелёного состояния.
- `alice_answer_tests.txx` — сгенерированный ИИ черновик набора e2e-тестов, который я использовал как отправную точку и адаптировал. Это не «готовый» артефакт, а подсобный материал.

## Главные выводы (из `problems.txt`)

1. **`Depends()` нужно указывать почти для каждого аргумента FastAPI-эндпоинта.** Ошибка 422 возникла именно из-за того, что в `get_jwt_payload` был передан `oauth2_scheme` вместо `Depends(oauth2_scheme)`.
2. **Не стоит пытаться усидеть на двух стульях в REST API.** Я одновременно соблюдал «чистый REST» и оптимизировал нагрузку, из-за чего появились дублирующиеся модели `User` / `UserListItem`, `Friend` / `FriendListItem`. В итоге это усложнило контракт.
3. **Роли и use case нужно проектировать до кода.** В версии на C++ я уже путался в правах; здесь пришлось явно разделить фиксированных админов ресурса и модераторов групп.
4. **Коды 200/201/204 полезны, но важнее договорённость.** Я сделал поддержку разных успешных кодов, как советовали, но понял: главное — чтобы спецификация и реализация совпадали.
5. **TDD/BDD сверху вниз работает, но внешние интеграции требуют отдельной инфраструктуры.** OAuth2 и email требуют собственные мок-серверы, nginx, фальшивый SMTP-узел, перегрузку DNS в Docker Compose и обработку множества ошибок.
6. **Сначала сервер и контракт, потом БД.** Для учебного проекта проще стабилизировать API и сервисы на моках, а слой хранения подключать последним.

## Чему я научился

- Как устроен **OAuth 2.0 Authorization Code Flow**: `client_id`, `redirect_uri`, `scope`, `state`, обмен `code` на `access_token`.
- Чем отличаются Google и VK: OpenID Connect против «почти OAuth2», `sub` против числового `id`, наличие/отсутствие `refresh_token`, разные поля профиля, PKCE у VK ID.
- Как работает **подтверждение email**: MX-записи, SMTP, HTML-письма, одноразовые ключи, TTL в Redis, защита от временных почт.
- Как **мокать внешние сервисы** и тестировать интеграции без реальных Google/VK.
- Как проектировать **схему БД** с каскадами, ограничениями и ролями.
- Почему «сделать всё сразу» — плохая стратегия для учебного проекта, и как вовремя остановиться.

# 3. VkazarmePython_Vibecoding — полная AI-assisted версия

## Что это

Тот же API социальной сети, но реализованный полностью — от спецификации до базы данных, WebSocket и тестов — в режиме **vibe coding**, то есть с активным использованием ИИ-ассистента. Это не «мой код без ИИ», а отдельный эксперимент: насколько хорошо я умею ставить задачу, декомпозировать её, проверять сгенерированный код и интегрировать его в архитектуру.

**Статус:** завершён как учебный эталон. README проекта описывает все шесть этапов: аккаунты, пользователи, друзья, подписки, группы, посты, комментарии, чаты, медиа, WebSocket и слой БД.

## Что реализовано

### Архитектура

```
HTTP request
  └─ app/api/            роутеры и Depends-провайдеры (только HTTP)
       └─ app/services/  бизнес-правила и проверки прав (без HTTP)
            └─ app/repositories/   интерфейсы (ABC)
                 ├─ memory/            in-memory реализации (по умолчанию)
                 └─ sqlalchemy_repos/  SQLAlchemy 2.0 + PostgreSQL/SQLite
```

- `app/container.py` — **composition root**: собирает репозитории, сервисы и `WebSocketHub` в один контейнер на инстанс приложения. Это даёт изоляцию состояния в тестах.
- `app/main.py` — фабрика приложения, централизованная таблица `exception → HTTP status`, middleware для фронтенда и CORS.
- `app/middleware.py` — раздача статического HTML-клиента и обработка preflight-запросов.
- `app/api/deps.py` — провайдеры зависимостей и извлечение JWT через `HTTPBearer`.
- `app/services/ports.py` — outbound-порт `ChatEventPublisher`, чтобы сервис чатов не зависел от WebSocket напрямую.

### Функциональность

- Регистрация и вход, bcrypt, JWT с claims `sub`, `exp`, `role`; фиксированные админы из `admins.json`.
- Профили пользователей, поиск, редактирование, удаление с каскадами.
- Друзья (симметричная связь), подписки на группы, модераторы.
- Группы, посты, комментарии; правила прав для владельцев, админов и модераторов.
- Личные и публичные чаты, участники, сообщения.
- Загрузка медиа: только изображения PNG/JPEG/GIF/WebP, лимит 5 МБ, публичная выдача по `/media/{id}`.
- Realtime: WebSocket `/ws/chats/{ChatID}?token=...` с событиями `newMessage`, `memberChange`, `ping/pong` и кодами закрытия 4400/4401/4403/4404.
- Два слоя хранения за одним интерфейсом: in-memory по умолчанию и SQLAlchemy/PostgreSQL при заданном `DATABASE_URL`.

### Тесты

- По README — **265 тестов**, из них **44 интеграционных**.
- Интеграционные тесты прогоняют SQLAlchemy-слой дважды: на SQLite и на реальном PostgreSQL через `testcontainers`.
- Unit-тесты сервисов работают на in-memory репозиториях.
- E2E-тесты используют `httpx`/`TestClient` и проверяют HTTP-контракт, включая WebSocket-сценарии и CORS.

### Инфраструктура

- `Dockerfile` для приложения.
- `requirements-dev.txt`: `pytest`, `pytest-asyncio`, `pytest-cov`, `httpx`, `aiosqlite`, `testcontainers[postgres]`.

# 4. ConsoleMatch3 — Match-3 в терминале

## Что это

Полноценная игра «три в ряд» для терминала на **чистом Python standard library**. Без сторонних пакетов, без сборки, без сети.

```
MATCH 3 ◆ terminal edition   SCORE   235
                             BEST    235
                             MOVES    29
                             TARGET 1,800
```

## Что внутри

- `match3.py` (~1000 строк) — curses-интерфейс: отрисовка поля, цвета, Unicode/ASCII-глифы, обработка клавиатуры и мыши, анимации, адаптация к размеру окна, сохранение рекордов.
- `match3_logic.py` (~380 строк) — чистый движок, не знающий про curses:
  - поиск горизонтальных и вертикальных групп;
  - каскады и гравитация;
  - подсчёт очков с бонусами за длинные группы;
  - поиск подсказки;
  - проверка наличия ходов и перемешивание поля;
  - снимки состояния для undo.
- `tests/test_match3_logic.py` — 20 unit-тестов на `unittest`: генерация поля, матчи, пересекающиеся группы, невалидные свопы, каскады, бонусы, dead board, shuffle, 40 ходов подряд.
- `Makefile` — `make run` и `make test`.
- `README.md` — правила, управление, опции CLI, заметки по терминалам.

## Чему я научился

- Разделять **UI и бизнес-логику**: движок тестируется без терминала.
- Работать с `curses`: цвета, пары цветов, `getch`, `KEY_RESIZE`, mouse events, ограничения отрисовки.
- Проектировать **чистые функции и структуры данных**: `Step`, `MoveResult`, `Snapshot`, `frozenset` координат.
- Писать алгоритмы: поиск групп, каскадное разрешение, gravity/refill, проверка «есть ли ход», эвристика подсказки.
- Делать CLI на `argparse` с валидацией аргументов, seed для воспроизводимости, `--zen`, `--ascii`, `--no-mouse`, `--no-save`.
- Сохранять состояние в JSON атомарно (через временный файл и `replace`).
- Писать тесты на стандартной библиотеке без внешних зависимостей.

## Запуск

```bash
cd ConsoleMatch3
python3 match3.py
python3 -m unittest discover -v   # 20 тестов
```

# 5. playwright_mailpit — стенд проверки email-регистрации

## Что это

Учебный стенд, который проверяет полный сценарий:

1. пользователь регистрируется;
2. приложение отправляет письмо с ссылкой подтверждения;
3. письмо попадает в **Mailpit** (локальный SMTP-сервер с веб-интерфейсом и API);
4. тест забирает письмо через API Mailpit, извлекает ссылку;
5. аккаунт подтверждается;
6. пользователь может войти.

## Что внутри

- `app/main.py` — FastAPI-приложение с in-memory хранилищами:
  - `POST /account/signup` — создаёт аккаунт и отправляет письмо;
  - `GET /account/signup/confirmation?id=...&key=...` — подтверждает аккаунт;
  - `POST /account/signin` — проверяет пароль и статус подтверждения;
  - `GET /health` — health-check для ожидания готовности.
- `app/main.py` использует `smtplib`, `email.mime.multipart` и HTML+plain-text письма.
- `docker-compose.yml` — три сервиса в одной bridge-сети: `app`, `mailpit`, `tests`.
- `tests/test_flow.py` — e2e-тест:
  - ждёт готовности приложения;
  - очищает ящик Mailpit;
  - проверяет 403 до подтверждения;
  - извлекает ссылку регулярным выражением из письма;
  - подтверждает аккаунт;
  - проверяет успешный вход и 404 для несуществующего пользователя.
- `tests/Dockerfile` — образ Playwright, готовый к расширению UI-тестами.

## Чему я научился

- Поднимать **изолированную сеть Docker Compose** и обращаться к сервисам по именам (`app`, `mailpit`).
- Работать с **SMTP** и MIME-письмами.
- Использовать **Mailpit API** для проверки почты в автотестах.
- Писать e2e-тест, который проверяет не только HTTP-коды, но и побочный эффект — отправленное письмо.
- Делать health-check и retry-ожидание готовности сервиса.
- Понимать, почему для тестов email лучше локальный SMTP, а не реальный почтовый провайдер.

## Запуск

```bash
cd playwright_mailpit
docker compose up --build
```

## Ограничения

- Основной сценарий проверяется через `requests` + Mailpit API; Playwright подготовлен в образе, но UI-тесты ещё не написаны.
- Хранилища in-memory: данные теряются при перезапуске.
- Пароли хранятся в открытом виде — это осознанно упрощённый учебный стенд, не production.

# 6. JWTPentest — мини-лаборатория по JWT

## Что это

Небольшой стенд для изучения того, как FastAPI проверяет JWT и как ведут себя тесты с валидными и истёкшими токенами.

## Что внутри

- `server.py`:
  - FastAPI-приложение с эндпоинтом `GET /token`;
  - `OAuth2PasswordBearer` для извлечения токена;
  - `jwt.decode` через PyJWT с алгоритмом HS256;
  - Pydantic-модель `JWTPayload` с полями `sub`, `role`, `exp`;
  - `ConfigDict(extra="ignore")`, чтобы игнорировать `iat`, `jti` и другие стандартные claims;
  - раздельная обработка `ExpiredSignatureError`, `InvalidTokenError` и `ValidationError`.
- `client.py`:
  - интеграционные тесты через `requests`;
  - генерация токена с валидным и истёкшим `exp`;
  - проверка 200 для валидного токена и 401 для истёкшего.

## Чему я научился

- Как устроен JWT: header/payload/signature, `exp`, `sub`, `role`.
- Как FastAPI извлекает Bearer-токен и как работает `Depends`.
- Как валидировать структуру payload через Pydantic и разделять ошибки «истёк» / «невалиден» / «неверная структура».
- Как писать интеграционные тесты против запущенного сервера.
- Почему секрет нельзя хардкодить в реальном проекте: здесь он вынесен в константу только для учебной лаборатории.

## Запуск

```bash
cd JWTPentest
uvicorn server:app --port 8080
# в другом терминале
pytest client.py -v
```

## Ограничения

- Это именно лаборатория, а не пентест-инструмент: нет брутфорса, подбора секрета, атак `alg=none` и т.п.
- Секрет и адрес сервера захардкожены для простоты.
